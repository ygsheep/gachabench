# P2 文件操作与回收站

依赖：P1 的 `assets`、`asset_ref` 与文件监听。

## 目标

让资产库能改名、移动、删除，且在改名前先把影响面算清楚：哪些提示词、分镜、workflow 提到了这个文件，改成什么，改动前后差异是什么。应用后可以回滚，删除进回收站而不是直接消失。

## 进入条件

- P1 的引用表 `asset_ref` 已有数据，`GET /api/media` 的路径校验已通过越界用例。
- 确认真实提示词正文里写的是文件名，不是占位符。样本 `04_正片_第4段_15s.md` 的 §② 直接写 `白陌_写实_四视图.png`，改名必须改正文。

## 范围

| 做 | 不做 |
| --- | --- |
| 计划、应用、回滚三态 | 不做正文编辑器（P4） |
| 文件名区间替换与逐文件差异 | 不做语义改名 |
| 备份、原子替换、大小写改名 | 不做跨卷移动 |
| 回收站、恢复、彻底清除 | 不做团队权限（v2） |
| 重复与未引用视图 | 不做自动清理 |

## 步骤

1. 建 `backend/modules/assets/plans.py` 与表 `operation_plans`：id、kind、payload_json、base_json、status、created_at、expires_at、applied_at、result_json。计划 30 分钟过期，过期后 `apply` 返回 `PLAN_STALE`。

2. 引用扫描补全。P1 已索引以下几类，P2 在 plan 阶段重新读文件确认行号：

| 来源 | 识别方式 | `kind` |
| --- | --- | --- |
| 提示词 §② 上传表 | 表格行里出现完整文件名 | `prompt_filename` |
| 提示词正文 | 正文任意位置的完整文件名 | `prompt_body` |
| 分镜表素材列 | 21 字段表最后一列的文件名 | `storyboard_material` |
| workflow json | `inputs` 里的字符串值等于文件名 | `workflow_input` |

匹配用转义后的完整文件名，前后不能紧邻字母、数字、下划线或汉字，避免 `A.png` 命中 `AA.png`。

3. 建 `backend/modules/prompts/rewrite.py`，先只提供区间替换：

```python
def apply_spans(text: str, spans: list[tuple[int, int, str]]) -> str
```

按偏移倒序替换，记录每个 span 的 `before` 与 `after`。替换完成后校验：把所有 span 反向还原，结果必须与原文完全相等。任何一条不符即抛错，不写盘。

4. 计划接口返回每个受影响文件的 `before`、`after` 与行号，前端用 `difflib` 之外的统一结构展示。统计 `stats.files` 与 `stats.refs`。

5. 应用顺序固定：

1) 校验计划未过期、文件哈希与 mtime 未变；
2) 在 `.gachabench/backups/<planId>/` 下按相对路径备份原文件与将被改写的文本；
3) 写 `.gachabench/journal/<planId>.json`，逐步记录 `rename`、`rewrite`；
4) 文件改名为同目录临时名，再 `os.replace` 到目标，确保同卷原子；
5) 按 span 改写引用文本，先写临时文件再替换；
6) 一个事务内更新 `assets.path`、`asset_ref` 与计划状态；
7) 删除 journal，保留备份 7 天。

任一步失败，按 journal 逆序还原，计划状态置 `failed`，`op_log` 记失败原因。

6. 只改大小写时，Windows 不认同名替换。先改成 `.tmp-<uuid>`，再改成目标名，中间不经过大小写比较。

7. 回收站：删除计划通过后，把文件移到 `.gachabench/trash/<YYYYMMDD>/<assetId>__<原名>`，`assets.status="trashed"`，`trash_entries` 记原路径与时间。恢复时目标路径已存在则追加 `_02`，并把新路径写回资产记录。彻底清除需要二次确认，删行、删块引用，不动其他文件。

8. 删除时不改写引用。引用会指向一个已进回收站的资产，详情与提示词页显示「引用的文件已删除，可恢复」，恢复后引用自动有效。

9. 重复检测：按 `sha256` 分组，`hash_status="quick"` 的文件不参与。未引用检测：`asset_ref` 中没有记录且不在回收站。

10. 接口：

| 方法与路径 | 说明 |
| --- | --- |
| `POST /api/assets/operations/plan` | `kind` 取 `rename`、`move`、`delete`，返回计划与差异 |
| `POST /api/assets/operations/{planId}/apply` | 应用，返回新哈希、失败项、统计 |
| `POST /api/assets/operations/{planId}/rollback` | 撤销本次应用 |
| `GET /api/assets/operations/{planId}` | 计划详情，用于刷新后恢复弹窗 |
| `GET /api/trash` | 回收站列表 |
| `POST /api/trash/{id}/restore` | 恢复 |
| `DELETE /api/trash/{id}` | 彻底清除 |
| `GET /api/assets/duplicates` | 重复分组 |
| `GET /api/assets/unreferenced` | 未引用文件 |

11. 前端：

- 多选后出现操作条：改名、移动、删除；
- 改名弹窗先请求计划，再展示受影响文件列表，逐文件展开差异，默认全选；
- `blocked` 项单独列出原因，不可勾选；
- 回收站作为资产页的集合入口，支持恢复与彻底清除；
- 重复与未引用作为两个内置集合，复用同一网格。

## 数据变更

新增 `operation_plans`、`trash_entries` 两张表；`assets.path` 仍唯一，改名只更新该列与 `updated_at`。

## 测试与验收

| 用例 | 判定 |
| --- | --- |
| 改名命中 50 个引用 | 应用后逐文件读取，只有目标文件名变化，其余字节完全一致 |
| 回滚 | 回滚后文件内容哈希与应用前相同，路径还原 |
| 只改大小写 | `A.png` 改为 `a.png` 成功，引用同步，macOS 与 Windows 行为一致 |
| 重名冲突 | 计划阶段返回 `NAME_CONFLICT`，不出现覆盖 |
| 文件被占用 | 模拟 `PermissionError`，返回 `FILE_BUSY`，已完成步骤回滚 |
| 计划过期 | 31 分钟后 apply 返回 `PLAN_STALE` |
| 回收站恢复 | 恢复后资产重新可见，引用自动有效 |
| 恢复撞名 | 已存在同名文件时落到 `_02`，不覆盖 |
| 删除带引用文件 | 计划列出引用数，确认后文件进回收站，引用显示可恢复 |
| 路径越界 | `move` 到工作区外返回 `PATH_INVALID` |
| 备份不刷索引 | `.gachabench` 下的备份与 journal 不出现在资产列表 |

## 风险与回退

改写正文是这段最危险的动作。所有替换都限制在命中文件名的字符区间内，写前做反向还原校验，写后重算文件哈希；任何一步失败都不落盘。

Windows 文件占用与长路径是主要外部风险。遇到 `PermissionError` 直接中止并回滚，不做重试循环。路径超过 260 字符时提示用户缩短目录，不在这一段引入长路径前缀。

回退方式：P2 不改旧表结构，关闭计划接口即可回到只读资产库；备份保留 7 天，可手工还原。
