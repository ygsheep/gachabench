01 · 缺口判断

缺的不是小说，是入口

GB 的真实缺口是输入侧没有入口：结构化提示词 md 全靠外部产出。NBE 只能填一半——给文本；「文本 → §①–§⑥」的改编在 v1 边界之外（/api/agent 501）。联网采集的性价比远低于直觉。

02 · 基建判断

高性价比在基建，不在业务

NBE 已踩完「FastAPI + React + Tauri 双形态」整套坑：前端自主托管、导出契约、设置模型、首屏缓存——四件搬过来，新增第三方依赖为 0。UI 只借交互模式，样式全部重写。

03 · 样式判断

一个组件都搬不动 X-1 / X-2

React 18 + JSX + 铜金双主题 vs React 19 + TS 6 + 零彩度金属灰 --gb-*。npm 包与组件不可共享；NBE 的 useState 编排要改写为 Query + zustand 分工。

红线与冲突

10 项，整合时必须服从
X-1 – X-10
X-1
设计系统

只借模式不借样式。颜色全走 --gb-*，状态用实线 / 虚线 / 斜纹；一个 JSX 都不复制。

X-2
框架代际

不共享 npm 包与组件。NBE 的 useState 编排要改写为 Query + zustand 分工。

X-3
数据模型

书库进 <工作区>/.gachabench/cards.db，服从 I-2 自包含；只有 UI 偏好进 localStorage。

X-4
v1 边界

采集 / 导入只到「文本」。不承诺「一键出剧本」；改编要做是新立项，不是本次整合。

X-5
铁律 I-1 + 行号可信度

textclean 禁止上 提示词/*.md 读取链（splitter / prompt_locator）。只做导入入口。

X-6
网络与合规

默认只做本地导入；联网采集默认关闭 + 免责 + 来源标注；字体解密不做（R2）。

X-7
依赖与打包

轻档零依赖是首选路径；重档 +6 依赖，且火绒会对新 hash 的 exe 重新拦截。

X-8
并发模型

调度器用 asyncio.Semaphore；不要在线程池里调 comfy.py，会卡死轮询。

X-9
进程模型

同进程挂 library router。不起第二个 sidecar、不引入第二套端口与生命周期。

X-10
设置双层

设置页必须显式分层（全局 / 本工作区），否则跨工作区污染——历史踩过。

R1 – R6
R1QuickJS 沙箱 + java.* 桥

唯一能想到的用途是「提示词变换脚本」，而 GB 的铁律是「正文字词一字不改」（I-1）。能力与约束方向相反。

R2字体解密 replaceFont

纯反爬对抗技术，GB 无此场景；且属「规避技术措施」，合规上最不该带进来的一项。

R3书源 DSL 全量解释器

1,300 行 + 6 依赖，只有做 C3 时才需要。轻档方案里它是纯负担。

R4EPUB3 导出

GB 产物是 mp4 / txt 工单，EPUB 无消费者。

R5第二个 sidecar 进程

双进程 = 双端口 / 双日志 / 双生命周期 / 双份杀软误报面。同进程挂 router 完全够。

R6直接复用 NBE 的 JSX 组件

代际 + 语言 + 设计系统三重不兼容（X-1 / X-2），复制过来等于重写两遍。

一页纸总结 方案待拍板

01能整合的是「能力」，不是「业务」——五项基建 / 模式（文本卫生、首屏缓存、设置模型、导出契约、偏好持久化）零新依赖、风险可控。
02业务链路上 NBE 只能补一半：它给文本，GB 缺的是「文本 → 结构化提示词」的改编，而那条线在 v1 边界之外（/api/agent 501）。
03联网采集是性价比最低的一项：+6 依赖 / +体积 / 合规面 / 与铁律相邻。建议做成默认关闭的独立可选模块，且砍掉字体解密。
04UI 一个组件都别搬：零彩度设计系统 + React 19 / TS 6 与 NBE 的 React 18 / JSX 不兼容，只借交互模式。
05先做 C1 + O2 + P2：三件事都打在 GB 自己的痛点上（无文本卫生、首屏扫盘即等、无设置界面），且不碰任何既有不变式。
